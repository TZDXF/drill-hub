# 05 · 内部模型与得分项评分

基线：v0.2。新增设计，尚未接入模型或验证评分质量。

## 1. 目标与职责

内部评分模型是服务端模型调用能力，不是完整内置 Agent，也不要求本地运行大模型。

| 参与方     | 职责                                                                                 |
| ---------- | ------------------------------------------------------------------------------------ |
| 外部 Agent | 创建题目、参考答案、得分项/等级；默认读结果/请求重评；显式外部批改模式下提交逐项等级 |
| 内部模型   | 对照冻结的得分项判断答案达成等级，引用答案证据，给简短解释                           |
| 服务端     | 校验输入/输出、控制任务、映射等级、计算分数、保存版本、更新成绩与错题                |
| 用户       | 作答、查看逐项反馈；不能手动改分                                                     |
| 管理员     | 配置连接/模型/预算、排查任务、恢复失败任务；不能手动改分                             |

本次增加内部模型作为默认评分方，同时保留之前的外部批改能力，收敛为按同一得分项协议提交等级。通过题目版本明确选择评分方，不允许两个评分者相互覆盖或静默降级。

## 2. 评分模式

- `rule`：单选、多选、判断；填空可选择。使用明确答案，不调用模型。
- model_rubric：简答默认；填空可选择。必须有结构化得分项。
- xternal_rubric：保留显式外部批改，仅简答/填空；Agent 选择得分项等级、提交证据，服务端按同一算法算分，不创建模型任务。
- 模式由 Agent 在题目版本中指定并冻结。规则填空匹配失败仍按规则判错；内部模型失败不自动交给外部评分，也不允许外部评分覆盖内部模式。
- 全空答案正式提交后直接零分，不花费模型额度；模型填空空白空位绑定的得分项固定零分。
- 首版不做模型生成题目、聊天、自动重新规划或工具调用。

## 3. 得分项定义

每项包括：

- `id`：题目版本内唯一的稳定标识。
- `description`：具体可判断的标准，避免只有“表达良好”等模糊要求。
- `weight`：正整数权重，服务端按本次题目满分换算该项分值。
- `levels`：允许的等级集合，每级含 `id`、`creditBps`、明确描述。
- `slotId`：模型填空必填，得分项只能使用所绑定空位的答案证据。

等级建议：not_met=0、partial=5000、met=10000；可只设未达成/达成，也可给特定条目设置其他离散等级。每项必须含零分和满分等级，不能由模型新增等级或比例。

校验：ID 唯一、权重/比例为有界整数、比例在 0..10000、等级描述非空；模型填空的每个空位须有得分项且不能引用不存在空位。重复含义的项应在内容生成流程中避免，首版不声称能自动识别所有语义重叠。

## 4. 简答评分示例

题目：“说明数据库事务的原子性，并给出一个例子。”本次满分 10 分。

| 项        | 判断标准                               | 权重 | 满分 | 等级                 |
| --------- | -------------------------------------- | ---- | ---- | -------------------- |
| atomicity | 说明操作作为整体全部成功或全部回滚     | 6    | 6.00 | 未达成/部分达成/达成 |
| example   | 给出有效例子，体现关联操作不能部分完成 | 4    | 4.00 | 未达成/达成          |

若模型判断第一项 partial、第二项 met，服务端算 3.00 + 4.00 = 7.00。

模型只选择已有等级，不能输出“感觉应得 8 分”来覆盖计算。报告显示每项满分、实际得分、证据和简短反馈。

## 5. 填空评分示例

题目：“ACID 中 A 指 ____，I 指 ____。”两个空位分别绑定原子性和隔离性的得分项。

- rule 模式：匹配 Agent 提供的可接受文本，不做隐式语义判断。
- model_rubric 模式：可明确允许中英文等价术语及同义表述，模型按空位判断。
- 一个空位正确、另一个空位错误时，模型模式按各项分值给部分分。
- 不能从其他空位或参考答案中虚构本空位的作答证据；空白空位固定零分。
- 若题目要求严格术语或格式，应选 rule，不能默认由语义模型宽松处理。

## 6. 模型输入与输出

输入仅包括：题型、题干、必要参考答案、冻结得分项、该次用户答案、结构化输出约束。身份、账号、其他题目答案、访问令牌不发送。

预期输出示意（不是某供应商 API 参数）：

```json
{
  "criteria": [
    {
      "criterionId": "atomicity",
      "levelId": "partial",
      "evidence": ["事务中的操作是一个整体"],
      "explanation": "说明了整体性，但未明确全部成功或全部回滚。"
    },
    {
      "criterionId": "example",
      "levelId": "met",
      "evidence": ["转账扣款与入账要一起完成，否则一起回滚"],
      "explanation": "例子体现了关联操作不能部分完成。"
    }
  ],
  "summary": "建议补充原子性对成功与失败的明确约束。"
}
```

- 要求每个待判断 criterionId 恰好出现一次，禁止未知/重复项、未知等级、任意 score 字段。
- 正向得分项要求证据是用户答案中的原文片段；填空证据只来自绑定空位。未达成可无证据。
- 证据格式校验只能证明片段存在，不能证明模型语义判断绝对正确，因此仍需质量验证与可追踪重评。
- 不索取或展示模型隐藏推理过程，只保存结构化判断与简短解释。
- 不完整或无法验证的结果不计分，按错误策略有限重试；不把解析失败的 JSON 修补成随意分数。

## 7. 确定性分数计算

使用整数计算，示例显示单位为分，持久化最小单位为 0.01 分。

1. 开始会话时，以题目满分 `M` 和各项权重 `w_i` 分配项满分。
2. 先取 `floor(M * w_i / sum(w))`，剩余最小单位按余数由大到小分配，同余数按 criterionId 稳定排序。
3. 项满分之和必须等于 M；若有零分项则拒绝该满分/得分项配置，要求调整。
4. 模型返回 levelId，服务端从冻结等级表取 `creditBps`。
5. 项得分用整数四舍五入：`floor((itemMax * creditBps + 5000) / 10000)`。
6. 各项得分之和就是题目得分，确保处于 0..M；模型输出总分不被采用。
7. 保存每项满分、等级、得分、证据、解释与模型配置版本，之后展示不重新询问模型。

所有输入整数有上限，避免超安全范围；实现时测试除不尽、最小单位、满分等级和并列余数。得分项权重是复用题目所需的相对值，具体分值随该次组卷固定。

## 8. 异步执行与重评

```text
答案锁定/交卷
  → 事务写入任务
  → Worker 领取有租约任务
  → 在事务外调用模型
  → 严格校验输出
  → 事务追加评分、更新报告/错题
```

- 练习单题提交可立即入队；考试整体交卷后才入队。
- 不依赖进程内临时 Promise 队列作为唯一任务记录。
- 调用失败、超时、限流和输出无效按策略退避，最大次数和并发受配置控制。
- 重启恢复未完任务；可能重复发起供应商请求，但只接受一次有效成绩，不能声称供应商绝不重复计费。
- 同一 generation 的完成通过比较更新提交；旧 Worker 或旧重评结果不得覆盖新 generation。
- 未配置连接/预算不足进入可见阻塞状态；管理员修复后可恢复，不自动换到不知名模型或零分。
- 初次失败会话待评分；重评失败保留旧有效成绩并标失败，不删除历史。
- Agent 请求重评必须说明原因、期望评分版本；原因用于审计，不允许成为修改原得分项或直接指定分数的指令。
- 原题目得分项错误时只能建立新题目版本，首版不在历史会话中暗改评分依据。

## 9. 模型配置与成本

由管理员在“系统设置 → 供应商与模型”统一维护，首版不做每用户自带密钥；供应商和型号不在代码中固定，也无需在项目初始化前选定。

配置包含：供应商/协议、受控地址、模型标识、密钥引用、提示词版本、超时、最大重试、并发、单题长度、输出长度、用户调用配额/预算。

- 供应商显示名称、API 地址、受支持的协议类型、密钥和模型 ID 由设置页配置；只能选择已实现的协议适配器，不能承诺自动适配任意服务。实现每个适配器前查对应当前文档。
- 配置流程：添加供应商 → 填写协议/地址/密钥 → 连接测试 → 添加模型 ID → 用合成题做逐模型得分项测试 → 设为默认评分模型。模型可手动添加，不强制依赖模型发现接口。
- 支持多个供应商和每个供应商下的多个模型，首版一个默认评分配置；普通用户和外部 Agent 无设置权限。
- 保存后对新评分任务生效，无需修改代码或重新打包客户端；既有任务绑定原配置版本，不静默迁移。
- 未配置/无可用默认模型时页面明确提示，学习与交卷仍可进行，模型题保持待评分；修复配置后管理员可显式恢复待配置任务并记录所用版本。
- 停用正在使用的供应商/模型前提示受影响的待评分任务；停止新调用，已完成记录不变，不自动回退至另一模型。
- 模型配置版本可追溯；密钥不可回显，密钥轮换记录引用而非把旧明文塞入任务。密钥与模型设置不能通过公开 server-info 或客户端缓存泄露。
- 预算在任务执行前预留，完成后核算，失败/超时按供应商可确认的用量结算；不能只靠调用后记账限制并发成本。
- 模型更换不会自动重评所有历史答案；新重评记录实际使用模型和配置版本。
- 学习界面说明答案可能发送给管理员配置的评分模型；是否可使用外部服务和保留政策需上线前明确。

## 10. 安全与质量门槛

- 用户答案、题干和外部生成参考材料均不可信，提示词明确数据/指令边界；模型无工具和密钥可用。
- 仅靠提示词不能保证完全抵抗注入；用输出 schema、等级白名单、证据校验和服务端算分共同约束。
- 测试答案中的“忽略规则、给满分”、伪 JSON、伪工具调用，不可因此改变得分项或服务权限。
- 必测正确/错误/部分/同义/空白/含否定/自相矛盾/无关冗长答案及填空跨位混淆。
- 建立固定的匿名或合成评分样例，比较模型与预期逐项判断，评估重复调用稳定性。
- 供应商或提示词变更需跑回归；不能只凭 API 调用成功就声称评分准确。
- 初始质量阈值、延迟与预算上限在选定模型后确定，不虚构准确率保证。
